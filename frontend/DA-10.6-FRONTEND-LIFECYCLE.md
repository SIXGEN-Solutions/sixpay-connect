# DA-10.6 — Frontend password lifecycle

## Scope

DA-10.6 completes the frontend side of the LOCAL password lifecycle introduced
by DA-10.1 through DA-10.5.

OIDC remains excluded because password lifecycle belongs to the IdP.

## Mandatory navigation

```text
Local login
    |
    v
backend AuthenticationSessionResponse
    |
    v
passwordChangeRequired?
   / \
 no   yes
 |     |
 v     v
app   /change-password
       |
       v
POST /api/v1/auth/password/change
       |
       v
GET /api/v1/auth/me
       |
       v
passwordChangeRequired=false
       |
       v
original returnUrl / application
```

The original return URL is preserved while the mandatory password-change route
is active and is consumed only after successful remediation.

## Route enforcement

`authenticationGuard` protects the application shell:

- anonymous -> `/login`
- authenticated LOCAL + `passwordChangeRequired=true` -> `/change-password`
- authenticated normal session -> application

`localPasswordChangeGuard` protects `/change-password`:

- anonymous -> `/login`
- OIDC -> `/`
- LOCAL -> allowed

The page can therefore also be used voluntarily by a normal LOCAL user.

## Screen

The page exposes:

- current password;
- new password;
- confirmation;
- minimum length rule;
- password-history rule;
- backend lifecycle/policy error feedback.

The frontend validates confirmation and the known initial length boundary.
The backend remains authoritative for policy, BCrypt verification, history and
expiration.

## Administrative reset

The existing administration reset remains separate. Its UI now explicitly
states that the password is temporary and that the user will be forced through
the change-password flow on the next LOCAL login.

## Defense in depth

If a business request is already in flight when a restricted session is
restored, the session-error interceptor redirects a credential-state 403 to
`/change-password` instead of incorrectly presenting the generic forbidden
screen.

## Validation

```bash
cd frontend
npm test
npm run build
```

Manual acceptance:

1. ADMIN resets a LOCAL user's password.
2. User logs in with the temporary password.
3. Login returns 200 and `passwordChangeRequired=true`.
4. Frontend navigates to `/change-password`.
5. Direct business routes redirect back to `/change-password`.
6. Wrong current password is rejected.
7. Reused password is rejected by backend history.
8. Valid new password succeeds.
9. Frontend reloads `/auth/me`.
10. `passwordChangeRequired=false`.
11. User reaches the original requested route.
12. OIDC login is never redirected to the LOCAL password lifecycle.
